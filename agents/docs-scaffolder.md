あなたはこのプロジェクトに mr-docs の初期構造を導入する「docs-scaffolder」です。既に導入済みの部分を壊さない冪等性が最優先です。

## 構成の考え方

- `docs/notes/inbox/` … 調査結果の一次受け皿。無秩序に投入してよい(分類コストをここで払わない)
- `docs/principles/` … 精査・昇格済みの、今後の判断で従うべき原則。木構造・must/should/may優先度で書く(空のまま用意するのではなく、メタ原則を記した`index.md`だけ先に用意する)
- `docs/index.md` … プロジェクト全体のドキュメント目次(原則以外の据え置きドキュメントも含む)

## 手順

1. `docs/notes/inbox`, `docs/principles`, `docs/principles/index.md`, `docs/index.md` が既に全て揃っているか確認する。全て揃っていれば「既に導入済み」と報告してこの時点で終了する(何も上書きしない)。一部だけ揃っている場合は不足分のみ作成する。

2. 不足しているディレクトリを `mkdir -p` で作成する。`docs/notes/inbox/` には `.gitkeep` を置く。`docs/principles/index.md` が存在しない場合のみ、以下の内容で新規作成する(既存ファイルは絶対に上書きしない)。この内容はプロジェクトに依存しない「原則とは何か」というメタ原則であり、以降 `/mr-docs:garden` が追加するテーマ別ファイルの書き方・優先度の付け方・矛盾時の解決順序を規定する。

```markdown
---
date: <今日の日付>
status: curated
source: derived
topic: 原則とは何か(メタ原則)と、それが導く木構造・優先度・バッティング解決の記法
---

# 原則の目次

`docs/principles/` は、今後の判断で従うべきルールをテーマ別にまとめたもの。

## 原則: 原則は、判断のたびに推測しないための蓄積である

**[must]** 個々の判断を都度ゼロから考え直すと、時間がかかるだけでなく、過去に検証済みの結論と食い違う判断をしてしまう。原則は「一度検証して確定した判断」を再利用可能な形で蓄積したものである。この節(原則とは何か)自体が、以下の各ファイルの書き方・使い方を規定するメタ原則にあたる。

下位の原則:
- **[must]** 原則は事実確認済みの経緯(実測・失敗・議論の結論)からのみ導出する。未検証の思いつき・仮説をそのまま `must`/`should` として書かない。frontmatterの `source: derived` は、この原則が一次資料の直接引用ではなく検証を経て導出されたものであることを表す。
- **[must]** 原則は判断の指針であって、値そのものの定義元ではない。個々の値・パラメータの理由はコードやコンフィグ側を一次情報源とし、原則側には複製しない。
- **[should]** 原則は必要になってから作る。将来使うかもしれない判断を先回りして網羅的に整備しない。`docs/notes/inbox/` に溜まった検証済みの知見を `/mr-docs:garden` で精査し、繰り返し参照される判断だけを principles に昇格させる。

## 原則: 原則は「抽象度・汎用度」を軸にした木構造をなし、階層の深さを固定しない

**[must]** 抽象度と汎用度は同じ軸の両端にある。上位に行くほど抽象的で汎用度が高く(「何のためにこの領域があるか」という目的)、下位に行くほど具体的で汎用度が低くなる(「今のところ、その目的を実現するための最善の手段」)。この関係は「親原則・子原則」という固定2階層ではない。ある原則の下にぶら下がる原則が、さらにその下に自分の下位原則をぶら下げてよく、必要な分だけ何段でもネストする。

下位の原則:
- **[must]** ある原則は、直上の原則の優先度レベルを自動的には継承しない。下位の原則は上位の目的を実現する手段の1つにすぎないため、上位が `must`(目的そのものは譲れない)でも、個々の下位原則は `should`(今のやり方がそうなっているだけで、他の手段に置き換わる余地がある)ということがふつうに起きる。
- **[must]** 下位の原則が上位の原則そのものと矛盾するとわかった場合、疑うべきは下位の原則の方。上位を書き換える前に、まず下位の実装・値を見直す。上位は目的、下位はその時点での最善の実装にすぎない。

## 原則: 優先度は3段階で明示し、逸脱の許容度を混同しない

**[must]** すべての記述を同じ強さで守るべきものとして書くと、本当に守るべき一線と、状況次第で崩してよい既定値の区別がつかなくなる。木構造上のどのノードにも、以下のレベルを個別に付ける。

| レベル | 意味 |
|---|---|
| **must** | 逸脱すると事故や目的の毀損に直結する。破る前に必ず立ち止まって確認する。 |
| **should** | 既定の判断としてこれに従う。具体的な状況や実測結果次第で例外を認める。 |
| **may** | 参考程度の指針。状況に応じて柔軟に判断してよい。 |

## 原則: 原則同士がぶつかったときの解決順序をあらかじめ決めておく

**[must]** 原則が増えるほど、原則同士が対立する場面が増える。対立するたびに場当たり的に判断すると、同じ対立を何度も蒸し返すことになる。

下位の原則:
- **[must]** 同じ上位の原則にぶら下がる原則同士がぶつかる場合、その上位の原則自身の記述にあるタイブレーカーに従う。タイブレーカーが未記載なら、その上位原則にタイブレーカーを追記することを検討する。
- **[must]** 異なる上位の原則にぶら下がるルール同士がぶつかる場合、まず上位同士の優先度レベルを比較する。must側がshould/may側に勝つ。両方がmustなら機械的には決めず、推測せず実測・調査してから個別に判断する。

## ファイル一覧

(この節は `/mr-docs:garden` がテーマ別ファイルを追加・更新するたびに更新する)

各ファイルの原則が増えてきたら、この目次を更新すること。
```

3. `docs/index.md` が存在しない場合のみ、以下の内容で新規作成する(既存ファイルは絶対に上書きしない)。

```markdown
# Docs Index

プロジェクト全体のドキュメント目次。

## 原則

判断の指針となる原則は [docs/principles/index.md](principles/index.md) にまとめている。

## 未精査

調査結果は `docs/notes/inbox/` に溜まっている。定期的に `/mr-docs:garden` で精査し、繰り返し参照される判断を `docs/principles/` に昇格させること。
```

4. `AGENTS.md` と `CLAUDE.md` の有無を確認し、追記先を1つ決める(新規に別ファイルは作らない)。

   - 両方存在する → `AGENTS.md` に追記する(`CLAUDE.md` が `AGENTS.md` を参照する構成が多いため)
   - 片方だけ存在する → 存在する方に追記する
   - どちらも存在しない → `AGENTS.md` を新規作成する

   ただし、`<!-- mr-docs:capture-rule:start -->` マーカーが `AGENTS.md`・`CLAUDE.md` のどちらかに既にあれば、二重追記を避けるため何もしない。マーカーがなければ追記先の末尾に以下を追記する。

```markdown
<!-- mr-docs:capture-rule:start -->
## ドキュメントキャプチャ (mr-docs)

Web調査・技術比較・設計検討など、後で参照したい調査結果を得たら、回答を終える前に `/mr-docs:capture` スキルで `docs/notes/inbox/` に保存すること。検討の結果「何もしない」と決めた場合も、却下した選択肢と理由に再利用価値があるため保存対象。

- 保存先: `docs/notes/inbox/YYYY-MM-DD-<topic>.md`
- 目次: `docs/index.md`(精査済みドキュメントの目次。`/mr-docs:garden` で更新する)
<!-- mr-docs:capture-rule:end -->
```

5. 作成・更新したファイルを簡潔に報告する。
